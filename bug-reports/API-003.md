# API-003: DELETE /booking/:id returns 405 Method Not Allowed for a non-existent booking instead of 404

| Field | Details |
|---|---|
| **Severity** | Low |
| **Priority** | P3 |
| **Status** | New |
| **Type** | Functional / Error handling |
| **Endpoint** | DELETE /booking/:id |
| **Reported by** | Herman Effendi |
| **Date reported** | 2026-10-29 |
| **Environment** | https://restful-booker.herokuapp.com, tested with Playwright 1.64.1, Ubuntu 24.04 |
| **Reproducibility** | 5 out of 5 attempts |

## Summary
Deleting a booking id that does not exist returns `405 Method Not Allowed`. The DELETE method is supported on this endpoint, so the status is misleading. A non-existent resource should return `404 Not Found`.

## Preconditions
- A valid authentication token (obtained from `POST /auth` with the documented practice credentials).
- The booking id used does not exist, for example `999999999`.

## Steps to Reproduce
1. Request a token: `curl -i -X POST https://restful-booker.herokuapp.com/auth -H "Content-Type: application/json" -d '{"username":"admin","password":"password123"}'`
2. Copy the `token` value from the response.
3. Send a DELETE request to a non-existent id: `curl -i -X DELETE https://restful-booker.herokuapp.com/booking/999999999 -H "Cookie: token=<TOKEN>"`
4. Observe the status code and the response body.
5. (Control) Create a booking, delete it with the same header, and confirm that a successful delete works. Then delete the same id a second time and compare the result.

## Expected Result
`404 Not Found`, consistent with `GET /booking/999999999`, which returns 404 for the same id.

## Actual Result
Status `405 Method Not Allowed`. [VERIFY: paste the exact status line and response body. Also note what the second delete of an already deleted booking returns.]

## Evidence
- Automated test: `tests/known-issues.spec.ts`, "API-003: deleting a non-existent booking should return 404" (marked with `test.fail()` while the issue exists).
- Comparison: `tests/read.spec.ts`, "a non-existent id returns 404" passes for GET.

## Impact
- **API consumers:** the status wrongly suggests that the method is not supported, which wastes debugging time. Clients cannot distinguish "already deleted" from "wrong request".
- **Idempotency:** repeated deletes of the same resource return an error code that is hard to handle consistently.
- **Severity rationale:** Low. The data is not affected and the behaviour is limited to an error case.
- **Priority rationale:** P3. A clean-up item for a future release.

## Possible Cause (hypothesis, not confirmed)
The delete route may fall through to a generic handler when the record is not found. This is a guess from black-box observation only.

## Suggested Fix
Return `404 Not Found` with a clear message when the id does not exist. Optionally document whether deleting an already deleted resource is treated as success or as an error.

## Workaround
Clients can treat both 404 and 405 as "nothing to delete" for this endpoint.
