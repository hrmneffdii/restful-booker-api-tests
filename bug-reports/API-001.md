# API-001: POST /auth returns 200 OK for wrong credentials instead of a 4xx status

| Field | Details |
|---|---|
| **Severity** | Medium |
| **Priority** | P3 |
| **Status** | New |
| **Type** | Functional / Security (authentication) |
| **Endpoint** | POST /auth |
| **Reported by** | Herman Effendi |
| **Date reported** | 2026-10-29 |
| **Environment** | https://restful-booker.herokuapp.com, tested with Playwright 1.64.1, Ubuntu 24.04 |
| **Reproducibility** | 5 out of 5 attempts |

## Summary
When the authentication endpoint receives wrong credentials, it responds with HTTP status 200 and a JSON body containing a `reason` message, instead of an error status such as 401. Clients that rely on the status code alone will treat a failed login as a success.

## Preconditions
- The API is reachable.
- No token is needed for this request.

## Steps to Reproduce
1. Send a POST request to `https://restful-booker.herokuapp.com/auth` with header `Content-Type: application/json`.
2. Use the body `{"username": "admin", "password": "wrong123"}`.
3. Observe the status code and the response body.
4. (Optional, with curl) `curl -i -X POST https://restful-booker.herokuapp.com/auth -H "Content-Type: application/json" -d '{"username":"admin","password":"wrong123"}'`
5. (Control) Repeat with the valid credentials from the API documentation and compare the responses.

## Expected Result
A 4xx status, preferably `401 Unauthorized`, with a message that the credentials are invalid, and no token in the body.

## Actual Result
Status `200 OK` with a body similar to `{"reason":"Bad credentials"}`. No token is returned. [VERIFY: paste the exact status line and response body.]

## Evidence
- Automated test: `tests/known-issues.spec.ts`, "API-001: wrong credentials should return a 4xx status" (marked with `test.fail()` while the issue exists).
- Related passing test: `tests/auth.spec.ts`, "wrong password does not return a token", which confirms that no token is issued.

## Impact
- **Integrations:** a client that checks only the HTTP status will consider the login successful, then fail later with a confusing error or, worse, continue in a broken state.
- **Monitoring:** failed login attempts are not visible as errors in status-code-based monitoring and alerting, which makes brute-force attempts harder to detect.
- **Security:** no token is issued, so access is not granted. The risk comes from misleading clients and weaker observability, not from an authentication bypass.
- **Severity rationale:** Medium. The API contract is misleading, but there is no direct unauthorized access.
- **Priority rationale:** P3. It should be fixed, but it does not block users.

## Possible Cause (hypothesis, not confirmed)
The handler may return the error object with the default success status instead of setting a 4xx status. This is a guess from black-box observation only.

## Suggested Fix
Return `401 Unauthorized` (or `400 Bad Request` for malformed input) with a consistent error body, and document the behaviour. Add a regression test that asserts the status code, not only the body.

## Workaround
Clients can check for the presence of the `token` field in the body instead of relying on the status code.
